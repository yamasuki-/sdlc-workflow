# /defect — 不具合対応フロー

> **配置と上書き**: このスキルのディレクトリは `${CLAUDE_SKILL_DIR}`。これが `~/.claude/skills/` 配下で、
> プロジェクトに `.claude/skills/defect/SKILL.md` がある場合は、そちらを Read してその指示に従い、以下は使わない
> （Claude Code は同名スキルを `~/.claude` 側で解決するため、プロジェクト版はこの方法で優先させる）。
> `<SDLC>/…` はワークフロー本体のファイル。`scripts/sdlc path <…>` で実際のパスを得てから読む。

通常の工程フローへの割り込み。原因が混入した工程から、影響範囲だけをやり直す。

```
起票 → ①再現テスト(Red) → ②原因特定 → ③混入/流出工程 → ④影響範囲 → ④' 対応方法の提案
     → ★人間ゲート（案の選定） → ⑤混入工程から差分やり直し（工程ごとにゲート） → ⑥検証・クローズ → 本線に復帰
```

不具合票の状態: 起票 → 原因判定済 → 承認済 → 修正中 → 検証済 → クローズ

## 0. 状況把握

`scripts/sdlc status` と `scripts/sdlc defect list` を実行する。
引数が DEF-ID ならその票を、説明文なら新規起票から始める。票の `status` で再開位置を決める:

| status | 再開位置 |
|---|---|
| 起票 | ① または ②（再現テストの有無で判断） |
| 原因判定済 | ★ 人間ゲート待ち（提示して停止） |
| 承認済 | ⑤ 開始（`defect start`） |
| 修正中 | ⑤ 継続（`/sdlc` の指示どおり工程スキルを実行） |
| （phase.json の step が verify） | ⑥ |

## テスト失敗のトリアージ（テスト工程で複数の失敗が出た場合）

起票の前に **investigator** を `mode=triage` で依頼し、失敗ごとに「製品起因 / テストコード起因 / 環境起因 / 不安定（flaky）」に
切り分ける。製品起因とテストコード起因は起票し（同じ原因と思われるものは 1 件にまとめる）、環境起因・不安定は人に報告する。

## 起票

```
scripts/sdlc defect new --title "<現象の要約>" --detected-in <工程> --severity <致命|高|中|低> \
  [--by auto] [--test <再現テストのパス>]
```
- テスト工程で失敗を検出した場合は `--by auto` で起票し、失敗したテストを `--test` に指定してよい。
- 票の「現象」「再現手順」を記入する（`state/defects/DEF-xxx.md` は Edit 可）。

## ① 再現テスト（Red）

- 再現テストが無ければ、**test-writer** エージェントに `test_dirs.regression` 配下へ作成させる（`trace:` には原因と思われる ID ではなく関連するテスト仕様 ID を書く）。
- 実行して**失敗すること**を確認し、票の `reproduction_test` に記入する。

## ②〜④ 原因特定・混入/流出工程・影響範囲

- **investigator** エージェントに `mode=bug` で依頼する（作成者・レビュアーとは別の独立エージェント）。
  渡すもの: 不具合票パス、再現テストパス、`<SDLC>/checklists/defect.md`、反復 2 回目以降は前回の結論
  （ただし鵜呑みにせずゼロベースで観察し直すよう指示する）。
- 調査は**エビデンス必須・推測禁止**。原因はファイル:行の粒度で、観測結果は票の「調査エビデンス」に生のテキストで残る。
  確信度が低い、または再現できない場合は、追加観測か人への確認事項を整理してから先に進む。
- investigator 終了後、`git status` で調査による変更（一時計装）が残っていないことを確認する。
- investigator が票に `cause_ids` / `injected_phase` / `escaped_phase` を記入し、
  `scripts/sdlc defect impact <DEF> --write` で `impact_ids` / `impact_files` / `rework_phases` を算出する。
- **reviewer** エージェントに `<SDLC>/checklists/defect.md` で原因判定をレビューさせ、結果を票の本文に追記させる。
- 混入工程が `external`（要求ドキュメント原文の誤り）の場合は、人に確認したうえで `/change` に切り替えてよい。

## ④' 対応方法の提案

- **solution-proposer** エージェントに依頼する。渡すもの: 不具合票（原因・影響範囲）。
  「あるべき姿（理想設計）」案と「最小修正」案を含む 2〜4 案と推奨案が `state/defects/<DEF>/proposal.md` に書かれ、
  票の `options` / `recommended` が記入される。案によってやり直し工程が変わる場合は推奨案に合わせて `rework_phases` を補正する。
- 自明な修正（原因が実装の局所的な誤りで、直し方が一意）の場合は提案を省略してよい（`options` は空のまま）。
- `scripts/sdlc defect analyzed <DEF>` を実行する。

## ★ 人間ゲート（原因判定・やり直し範囲の承認）

次を提示して**停止する**:
```
## 不具合 <DEF> の原因判定・やり直し範囲の承認依頼
- 現象 / 重大度:
- 原因（トレース ID・ファイル:行）と根拠となるエビデンス:
- 混入工程 / 流出工程と見逃し理由:
- 対応方法の選択肢: A) 理想 … / B) 最小修正 … （推奨と理由。あるべき姿との乖離・技術的負債）
- やり直し工程: <rework_phases>（承認すると該当工程のゲートは「再承認要」になります）
- 影響範囲: <impact_ids / impact_files の要約>（範囲外の作業は継続します）
承認と案の選定は端末で: scripts/approve defect <DEF>
```

## ⑤ 混入工程から差分やり直し

1. `scripts/sdlc defect start <DEF>` — 不具合対応モードに切り替わり、影響範囲内の本線タスクは停止（blocked）される。
   理想案を選ばなかった場合は、先送りにした技術的負債を `scripts/sdlc decision add` で記録する。
2. `/sdlc` の指示どおり、やり直し工程の工程スキルを順に実行する。工程スキルは
   `<SDLC>/phase-flow.md` の「差分やり直し」に従い、**影響範囲の ID だけ**を対象にする。
3. 各やり直し工程は通常どおりレビュー → 人間ゲート（`scripts/approve <工程>`）→ `scripts/sdlc phase advance`。
4. 実装のやり直しでは、再現テストが Red であることが TDD ガードの条件になる（再現テスト → 修正）。

## ⑥ 検証・クローズ

1. `project.yaml` の `commands.test` で再現テストが Green、回帰テストを含め全件成功を確認する。
2. **再発防止**:
   - 流出工程のプロジェクト固有レビュー観点 `rules/review-<流出工程>.md` に `- [DEF-xxx] 観点` を追記する
     （無ければ `<SDLC>/templates/rules/review.md` を雛形に作る。本体のチェックリストは全プロジェクト共通なので編集しない）。
   - 混入工程と対になるテスト仕様にこの不具合を検出するケースが追加されていることを確認する（⑤で追加済みのはず）。
   - 票の「再発防止」節を記入する。
3. `scripts/sdlc defect close <DEF>` — 全テスト成功を確認してクローズし、本線の工程・停止タスクを復帰させる。
4. `git add -A && git commit -m "<DEF>: クローズ"`。`/sdlc` で本線を再開する。

## 並行中タスクの扱い

- 影響範囲外の本線タスクは継続してよい（`scripts/sdlc tasks next --main`）。書き込みガードは
  承認済みの不具合ゲートがあり、影響ファイル外であれば再開先工程への書き込みを許可する。
- 影響範囲内のタスクは `blocked` のまま、クローズ時に自動で `pending` に戻る。
