# Claude Code 向け SDLC ワークフロー 提案仕様書

## 0. この文書の使い方（受け取り側プロジェクトへの指示）

この文書は、Claude Code 上で動かすソフトウェア開発ワークフローの**提案仕様**です。
受け取ったプロジェクトでは、次の手順で進めてください。

1. 現行ワークフロー（`.claude/` 配下、`CLAUDE.md`、hooks、スクリプト等）を読み、構成を把握する
2. 本書「11. 比較チェックリスト」の各項目について、現行の実装状況を記入する
3. 項目ごとに「本案採用 / 現行維持 / 統合（両方の良い点を組み合わせる）」を判定し、理由を書く
4. 比較結果と作り直し方針をレポートにまとめ、**人の承認を得てから**作り直しに着手する
5. 作り直しは本書「12. 推奨構築順」に沿って段階的に行う

本書の「必須要件」（1章）は判定対象外です。現行が満たしていない場合は必ず本案側に寄せてください。

---

## 1. 必須要件

| ID | 要件 |
|---|---|
| MUST-1 | ソフトウェア開発工程単位で進める（要求整理・分析 → 要件定義 → 設計 → 実装 → テスト） |
| MUST-2 | 要求が書かれたドキュメントを入力とする |
| MUST-3 | 並行して行えるタスク単位で処理を進められる |
| MUST-4 | 各工程でレビュー後に**人によるゲート**を設ける |
| MUST-5 | **TDD** で進める |
| MUST-6 | 入力形式は Excel / Word / PowerPoint / Markdown のいずれにも対応する |
| MUST-7 | 言語・テストフレームワークはワークフロー本体に持たず、プロジェクト固有情報として扱う |
| MUST-8 | Claude Pro プランの使用量を前提とした並行度にする |
| MUST-9 | 承認記録はファイルで残す |
| MUST-10 | 不具合発生時は原因を特定し、原因が混入した工程からやり直す |

---

## 2. 全体構成（3層）

```
/sdlc（最上位オーケストレーター）
 │  状態ファイルを読み、現在工程・ゲート状況を判定して次の工程を起動するだけ
 │
 ├─ 工程ワークフロー（全工程が同じ型）
 │    計画 → タスク分解(DAG) → 並行実行 → 統合 → レビュー → 人間ゲート
 │
 └─ タスク（並行実行の単位）
      サブエージェント／worktree で独立に処理し、成果物＋自己検証結果を返す
```

設計方針:
- 最上位は「何をするか」を持たず、**状態管理とルーティングに徹する**
- 工程ごとのロジックは各工程スキルに閉じ込める
- 全工程が同じ「共通フローの型」に従うことで、hooks・ゲート・再開処理を共通化する

---

## 3. 工程定義（V字モデル）

| 工程 | 主な成果物 | 対になるテスト（TDD の先行作成） |
|---|---|---|
| 0. 取り込み | 要求ドキュメントの構造化（要求 ID 付与・出典箇所・確信度） | — |
| 1. 要求整理・分析 | 要求一覧、曖昧点・矛盾・欠落の指摘、質問リスト | — |
| 2. 要件定義 | システム要件（SR-ID）、非機能要件 | 受入／システムテスト仕様 |
| 3. 基本設計 | アーキテクチャ、モジュール分割、IF 定義 | 結合テスト仕様 |
| 4. 詳細設計 | モジュール内設計 | 単体テストコード（Red の状態で作成） |
| 5. 実装 | コード（Red → Green → Refactor） | 単体テストを通す |
| 6. 結合テスト | 結合テスト実装・実行 | 3 で作った仕様を実行 |
| 7. システム／受入テスト | 試験結果、要件カバレッジ報告 | 2 で作った仕様を実行 |

### TDD の位置づけ
- 実装工程だけでなく、**V字の左側の工程で右側のテストを先に作る**
- 実装工程は、詳細設計で作成済みの失敗テストを通す形で進める

### トレーサビリティ
- 全成果物に ID を付け、`REQ → SR → 設計 → テスト → コード` で双方向に追跡できるようにする
- トレース情報は不具合時の原因特定と影響範囲分析にも使う

---

## 4. 工程内の共通フロー

1. **計画**: 前工程の承認済み成果物を入力に、作業範囲を決める
2. **タスク分解**: `tasks.yaml` に依存関係と「担当ファイル」を明記する（同じファイルを触るタスクは並行させない）
3. **並行実行**: 依存のないタスク群をサブエージェントに配布する（並行度は 6 章）
4. **統合**: 結果をマージし、整合性チェック・テスト実行を行う
5. **レビュー**: 作成者とは**別コンテキスト**のレビュー用エージェントがチェックリストで確認し、指摘 → 修正をループする
6. **人間ゲート**: レビュー報告を提示して停止する。人が承認するまで次工程に進めない

---

## 5. 入力形式への対応

取り込み工程に形式別の**変換アダプタ層**を置き、共通中間形式に変換する。後工程は中間形式のみを扱う。

```
入力（xlsx / docx / pptx / md）
   ↓ 形式別アダプタ
共通中間形式（Markdown ＋ 出典メタデータ）
   ↓
要求整理・分析（以降は形式を意識しない）
```

| 形式 | 出典の記録単位 | 注意点 |
|---|---|---|
| Excel | シート名＋セル番地 | 結合セル・表形式の要求一覧を行単位で展開 |
| Word | 見出し階層＋段落番号 | 表・箇条書き・変更履歴の扱い |
| PowerPoint | スライド番号＋図形 | 図・構成図・権限表は画像化して読み取り、確信度を付与 |
| Markdown | 見出し＋行番号 | ほぼそのまま |

- 形式の追加はアダプタの追加だけで済む構造にする
- 読み取りの確信度が低い箇所は、要求整理・分析工程の質問リストに回す

---

## 6. 並行度（Pro プラン前提）

- 同時実行は**最大 2 タスク**。`tasks.yaml` から依存のないものを 2 件ずつバッチ実行する
- worktree 分離は実装・テスト工程のみ（文書工程は担当ファイル分割で十分）
- レビューは並行させず 1 エージェントで実施する
- 使用量上限で途中停止しても再開できるよう、**タスク単位で `state/` に進捗を書き**、`/sdlc` 再実行で続きから再開する

---

## 7. プロジェクト固有情報

ワークフロー本体は言語非依存とし、言語固有の情報はすべて `project.yaml` に置く。

```yaml
# project.yaml
language: ""
test_framework: ""
commands:
  test: ""
  lint: ""
  coverage: ""
coverage_threshold: 0
src_dir: ""
test_dir: ""
```

- `/sdlc-init` で対話的に作成する
- hooks・各エージェントは `project.yaml` のコマンドを呼ぶだけにし、言語固有の処理を持たない

---

## 8. 人間ゲートと承認記録

### ゲートファイル

```
state/gates/<工程>.md
  工程 / 承認者 / 日時
  判定：承認 ・ 差戻し ・ 条件付き承認
  対象成果物とそのハッシュ
  コメント・条件
```

### 強制の仕組み
- 次工程の開始時、hook が「判定が承認」かつ「成果物ハッシュが一致」を確認する（**承認後に成果物が変わったらゲート無効**）
- Claude による `state/gates/` への書き込みは hook で禁止する
- 承認は**人が自分で実行する `scripts/approve`** で記録する（Claude 側のコマンドにすると自己承認の抜け道になるため）

---

## 9. TDD の強制

- 失敗するテストが無い状態での `src_dir` 編集を hook で拒否する（判定は `commands.test` の結果を使用）
- **test-writer と implementer を別エージェント**にし、テストを実装に合わせて書き換える事故を防ぐ
- 既存テストの削除・期待値の変更はレビュー対象として明示的に報告させる

---

## 10. 不具合対応フロー

通常の工程フローとは別の**割り込みフロー**として持ち、原因判定の結果に応じて工程を巻き戻す。

```
不具合検出（テスト工程で自動起票 or 人が /defect で起票）
   ↓
① 再現テスト作成（Red）        … まず不具合を再現する失敗テストを書く
   ↓
② 原因特定（トレース逆追跡）    … テスト→コード→詳細設計→基本設計→SR→REQ
   ↓
③ 混入工程・流出工程の判定
   ↓
④ 影響範囲分析                  … 混入箇所から下流のトレース ID を洗い出す
   ↓
★ 人間ゲート（原因判定・やり直し範囲の承認）
   ↓
⑤ 混入工程から差分やり直し（通常の工程フローを影響範囲だけ再実行）
   ↓
⑥ 再現テストが Green ＋ 回帰テスト全通過を確認 → 不具合クローズ
```

### 混入工程の判定
上流から順に「その工程の成果物は正しかったか」を判定し、最初に誤りがあった工程を混入工程とする。

| 誤りがあった成果物 | 混入工程 | やり直し開始点 |
|---|---|---|
| 要求ドキュメント原文そのもの | 外部（発注元） | 人に確認・要求変更として扱う |
| 要求の解釈・抜け | 1. 要求整理・分析 | 工程 1 |
| システム要件 | 2. 要件定義 | 工程 2 |
| アーキテクチャ・IF | 3. 基本設計 | 工程 3 |
| モジュール内設計 | 4. 詳細設計 | 工程 4 |
| コード | 5. 実装 | 工程 5 |
| テスト仕様・テストコード自体の誤り | 対応する V 字左側の工程 | その工程 |

あわせて**流出工程**（本来どのレビュー・テストで見つけるべきだったか）も判定する。

### 不具合票

```
state/defects/DEF-xxx.md
  現象 / 再現手順 / 検出工程 / 重大度
  再現テストのパス
  原因（該当トレース ID・該当箇所）
  混入工程 / 流出工程と見逃し理由
  影響範囲（再実施対象の成果物・タスク一覧）
  状態：起票 → 原因判定済 → 承認済 → 修正中 → 検証済 → クローズ
```

### やり直しの仕組み
- **ゲートの無効化**: 混入工程以降のうち影響範囲に含まれる工程のゲートを「再承認要」にする。成果物ハッシュ方式なので修正すれば自動的に無効になり、明示的にも不具合 ID を記録する
- **差分やり直し**: 影響範囲のトレース ID だけを対象に `tasks.yaml` を再生成し、通常の工程フローを回す。全面やり直しにはしない
- **並行中タスク**: 影響範囲外は継続、影響範囲内は停止
- **テストの追加**: 再現テストを回帰テストとして残し、混入工程と対になるテスト仕様にもケースを追加する
- **再発防止**: 流出工程のレビューチェックリストに観点を追加する
- **原因特定は独立エージェント（investigator）が担当**し、作成者・レビュアーに自己弁護させない

## 11. ディレクトリ構成

```
CLAUDE.md                        … 全体ルール（TDD 必須、ゲート必須、ID 体系）
project.yaml                     … プロジェクト固有情報
.claude/
  skills/ (or commands/)
    sdlc/                        … 最上位オーケストレーター
    sdlc-init/                   … project.yaml 作成
    phase-intake/                … 工程 0（形式別アダプタを含む）
    phase-requirements/          … 工程 1
    phase-system-requirements/   … 工程 2
    phase-basic-design/          … 工程 3
    phase-detailed-design/       … 工程 4
    phase-implementation/        … 工程 5
    phase-integration-test/      … 工程 6
    phase-system-test/           … 工程 7
    defect/                      … 不具合対応フロー
  agents/
    analyst                      … 要求整理・要件定義
    designer                     … 基本設計・詳細設計
    test-writer                  … テスト仕様・テストコード作成
    implementer                  … 実装
    reviewer                     … 各工程のレビュー
    investigator                 … 不具合の原因特定
  settings.json (hooks)
    - ゲート未承認／ハッシュ不一致なら次工程の開始を拒否
    - state/gates/ 配下への Claude の書き込みを拒否
    - 失敗するテストが無い状態での src_dir 編集を拒否
scripts/
  approve                        … 人が実行する承認記録スクリプト
docs/<工程>/                     … 各工程の成果物
state/
  phase.json                     … 現在工程、通常モード／不具合対応モード（対象 DEF-ID）
  tasks.yaml                     … タスク DAG と進捗（再開用）
  gates/<工程>.md                … 工程ゲートの承認記録
  gates/defect-DEF-xxx.md        … やり直し範囲の承認記録
  defects/DEF-xxx.md             … 不具合票
```

- 同等なら、既存の資産・運用に影響が少ない方を選ぶ
- 「統合」を選んだ場合は、どの要素をどちらから取るかを明記する

## 13. 推奨構築順

1. `CLAUDE.md`・`project.yaml`・`/sdlc-init`（土台）
2. `state/` の形式と `/sdlc`（状態判定・再開）
3. ゲートと TDD の hooks、`scripts/approve`（強制力の担保）
4. 工程内共通フローの型（タスク分解・2 並行実行・統合・レビュー）
5. 工程スキル（0 → 7 の順。工程 0 の形式別アダプタを含む）
6. 不具合対応フロー（`/defect`、investigator、やり直し処理）

各段階の完了時に、小さなサンプル要求ドキュメントで動作を確認してから次に進むこと。
